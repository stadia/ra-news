### Anti-Hallucination Protocol — Verify Before You Write

AI assistants produce confident-wrong code when statistical priors from training
data override observed facts in the current project. These 6 rules force
verification at the exact moments hallucination is most likely.

1. **Verify before you write.** Never reference a column, association, route, helper, method, class, partial, or gem you have NOT verified in THIS project via a tool call in THIS turn. If it's not verified here, verify it now. Never invent names that "sound right."
2. **Mark every assumption.** If you must proceed without verification, prefix the relevant output with `[ASSUMPTION]` and state what you're assuming and why. Silent assumptions are forbidden. "I'd need to check X first" is a valid and preferred answer.
3. **Training data describes average Rails. This app isn't average.** When something feels "obviously" like standard Rails, query anyway. Factories vs fixtures? Pundit vs CanCan? Devise vs has_secure_password? Check `rails_get_conventions` and `rails_get_gems` BEFORE scaffolding anything.
4. **Check the inheritance chain before every edit.** Before writing a controller action: inherited `before_action` filters and ancestor classes. Before writing a model method: concerns, includes, STI parents. Inheritance is never flat.
5. **Empty tool output is information, not permission.** "0 callers found," "no validations," or a missing model is a signal to investigate or confirm with the user — not a license to proceed on guesses. Follow `_Next:` hints.
6. **Stale context lies. Re-query after writes.** After any edit, tool output from earlier in this turn may be wrong. Re-query the affected tool before the next write.

## Phlex conventions (phlexed)

- Before writing ANY Phlex view, read `.phlexed/registry.json` for the list of
  available components, their props, variants, and sizes.
- Compose pages from registered components. Do not inline raw HTML/Tailwind when a
  component exists for that pattern.
- Follow the component library's variant/size naming exactly. `variant: :primary`,
  not `class: "btn-primary"`. The library's prop DSL is the canonical interface.
- If a pattern has no matching component, create one via `/phlexed-component` before
  building the page. Do not open-code a new pattern inline.
- Respect the library namespace: `PhlexyUI::Button` (not `Button`),
  `ShadcnPhlexcomponents::Dialog` (not `Dialog`). The registry lists the full class name.

## Styling rules (phlexed)

- Before writing ANY styles, read `.phlexed/style-registry.json` (generated by
  `/phlexed-setup` when DaisyUI/Tailwind is detected). It lists the design system's
  vocabulary and anti-patterns.
- Use component props for styling (`variant: :primary`, `size: :lg`), not raw CSS
  classes. The library maps props to the correct DaisyUI/Tailwind classes.
- Use DaisyUI semantic colors (`bg-primary`, `text-base-content`), never hardcoded
  values (`bg-blue-500`, `text-#333`). Semantic colors respect theme switching.
- Use DaisyUI component classes (`btn`, `card`, `badge`) when no Phlex component
  exists. Do not recreate them with Tailwind utilities.
- Never add inline `style=""` attributes to Phlex components.
- Never create custom CSS files when the design system can handle it. If a new color
  or utility is needed, add it as a theme extension in `tailwind.config.js`, not as
  a one-off class.
- When switching themes (dark mode, custom themes), update
  `<html data-theme="…">` via the layout, not via per-component overrides.
